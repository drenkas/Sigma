# ZENTAB — browser control

Кодова назва тікета: **ZENTAB**. Обсяг оновлено 2026-10-09 після вибору користувача: поточні вкладки звичайного Chrome — основний режим; окрема видима внутрішня Chrome for Testing — тільки за явною командою. Codex App, Zen-розширення та керування іншими macOS-застосунками до цього MVP не входять.

## Режими

| Команда/дія | Браузер | Межа |
|---|---|---|
| Browser control → Connect у режимі `chrome` | Відкритий Chrome користувача, Chrome 144+ | Користувач окремо вмикає вбудований remote debugging і приймає Chrome-підтвердження. Sigma бачить доступні цілі, але приєднується лише до вкладки, яку користувач вибрав у Sigma. Дозвіл Chrome може охоплювати весь браузер; Sigma не показує модельному інструменту довільні CDP-команди. |
| Точний користувацький prompt `/browser internal` | Видима окрема Chrome for Testing зі свіжим профілем | Профіль у `DATA_DIR/browser-use/internal/`; авторизацію треба виконати вручну. Немає копіювання cookies, Chrome-профілю чи токенів. Після першої сторінки дозволена навігація лише на HTTP(S). |
| Точний користувацький prompt `/browser chrome` | Перехід до звичайного Chrome | Зупиняє лише власний внутрішній процес, якщо він запущений, і повертає ручне підключення до Chrome. Автоматичної підміни режиму немає. |
| Browser QA | Ізольована статична QA-сторінка | Існуючий QA-контракт лишається окремим і незмінним; він не замінює керування довільними вкладками. |

У звичайному режимі Sigma може прочитати тільки короткий DevToolsActivePort descriptor зі стандартного каталогу Chrome після явного Connect. Якщо descriptor недоступний, UI приймає лише loopback адресу й порт, які користувач скопіював зі сторінки `chrome://inspect/#remote-debugging`. Підключення відбувається без `/json/version`, сканування портів, розширення чи зміни Chrome startup flags. Chrome показує власний дозвіл перед WebSocket-підключенням. Він може надати доступ до всього браузера; Sigma інвентаризує вкладки, але приєднує й обслуговує лише явно вибрану ціль.

Внутрішній режим запускає лише наявний Chrome for Testing як видиме окреме вікно зі свіжим профілем під `DATA_DIR/browser-use/internal/`. Він використовує watchdog-owned `--remote-debugging-pipe`, без loopback debug-порту, локального DevTools HTTP сервера або читання Chrome-профілю користувача. Disconnect, Stop, завершення сервера чи збій зупиняють лише зареєстровану групу цього процесу; профіль лишається на диску. Внутрішній браузер не відкривається автоматично після невідомого результату або перезапуску.

## Доступ і дії

Панель Browser control доступна лише для активної supervised root-сесії. Кожен виклик перевіряє активний режим і вибрану вкладку. Для browser tools обрана Pi-модель мусить приймати зображення. Набір дій фіксований: screenshot, click, type, scroll, key і navigate; довільний JavaScript, DOM-значення, cookies, мережевий трафік і довільні CDP-команди модель не отримує.

У режимі Ask кожний виклик браузерної дії отримує одноразове підтвердження перед dispatch; у Full діють звичайні правила Full без окремого ручного кроку на кожну дію. Browser tools доступні лише для активної supervised root-сесії та Pi-моделі, що приймає зображення. Модель не може сама перемикати режим, надавати доступ чи вибирати вкладку. Координати прив'язані до останнього скриншота, вибраної вкладки й покоління документа; після зміни сторінки потрібне нове спостереження. Введення тексту й клавіш блокується для видимих credential/verification полів, фреймів, які неможливо перевірити, та неперевіреного фокусу.

У коді Browser control передбачено блокування власних API та dev-UI loopback endpoints у `browser_navigate` й inventory/picker, а також перевірки поточної top-frame URL перед browser діями та screenshot. Фактичну поведінку при redirect і user navigation на control page, повторну перевірку після approval та недоставку screenshot підтверджено CFT-тестом 2026-10-09 (див. «Перевірка й межі доказу»). Окремо доведено, що Pi Bash sandbox блокує loopback-порти API та Vite proxy, зберігаючи доступ до звичайної project network. Команда `dev:web` запитує порт 4317; окремий Vite boundary proof на власному ephemeral порту 50958 підтвердив, що `strictPort` відхиляє зайнятий запитаний порт без fallback listener і запускається на вільному запитаному порту.

Перед screenshot Sigma перевіряє видимі credential/verification поля у звичайному документі, доступних same-origin фреймах і відкритих shadow roots; якщо видимий frame не можна перевірити, знімок блокується повністю. Такі перевірки не читають чи не передають значення полів і не охоплюють закриті shadow roots, canvas, картинки, усі сторінкові секрети чи інші довільні чутливі дані. Це не гарантія редагування зображень. Координатні дії консервативно вимагають незмінного PNG до та після підтвердження; анімація, блимаючий курсор або інша рухома сторінка можуть спричинити відмову й потребу в новому скриншоті. Усі login, парольні менеджери, OTP і введення секретів слід виконувати вручну.

Скріншоти показуються у Sigma, зберігаються як приватні browser-use артефакти в локальних даних Sigma й передаються в image-capable Pi-контекст. Тому вибрана сторінка може лишитися в історії Pi/провайдера та локальній історії Sigma. Звичайний текст, переданий у `browser_type`, також може зберігатися в історії інструментів; використовуйте лише несекретний текст. Дії й результати мають durable статуси. Якщо зв'язок губиться після dispatch, результат — `unknown`: Sigma не повторює клік, введення чи навігацію автоматично. Disconnect і Stop закривають лише власне WebSocket/CDP-підключення або вибраний внутрішній процес; вкладки звичайного Chrome не закриваються.

Команда перемикання режиму доступна лише з користувацького prompt, зберігається з command ID до запуску й не повторюється після рестарту. Повтор того самого ID повертає збережений стан. Після невідомого результату спочатку перевірити панель Browser control і фактичний стан браузера.

## Перевірка й межі доказу

R4 source candidate `421aa721…` зібрано пакувальником без розбіжностей: `desktop:package` завершився з exit 0, збіглися 36 manifest hashes, шість emitted owner-модулів, raw owners/contracts і 22 файли frozen source (`.scratch/chrome-acceptance-20261009/r4-package-proof.json`). Після serial `npm run build` теж завершився з exit 0. Vite boundary proof підтвердив відмову при зайнятому запитаному порту, відсутність fallback listener, запуск на вільному запитаному порту та cleanup (`.scratch/chrome-vite-boundary-proof-2OFEuv/proof.json`).

Повний serial `npm run check` (2026-10-09, після виправлень тестів) завершився з exit 0: **178/178 passed**, без cancelled/skipped; `npm run build` теж exit 0. Попередній результат 175/177 мав дві причини в тестах, а не в продукті. (1) Свіжий CFT-профіль із підміненим HOME під час першої навігації чекав на macOS Keychain (від 2 до понад 10 с при ліміті 8 с). Синтетичні тестові профілі тепер запускаються з `--use-mock-keychain` (`chrome-test-fixture.ts`), а Internal Chrome на macOS отримує справжній HOME облікового запису й нативне шифрування (профіль лишається приватним у `DATA_DIR`), тож перша навігація займає ~60 мс. (2) Після фази redirect тест повторно вибирав вкладку й клікав зі старим observationId, який продукт правильно відхиляв. Watchdog-тест тепер чекає, поки обгортка `exec` замінить себе процесом Chrome.

Independent whole-source review не знайшов додаткового підтвердженого material finding. У запакованому сервері рання відмова для control-page destination пройшла у 72 комбінаціях; approvals, actions та artifacts лишилися нульовими (`.scratch/chrome-r4-review-20261009/early-denial.json`). Повний CFT-тест тепер доходить до fixture і підтверджує від'єднання вибраної вкладки після redirect та user navigation на control page, скасування screenshot, що чекав approval, і відсутність збережених артефактів. Це runtime-доказ для CFT, а не для особистого Chrome.

Таймаути `Page.navigate` / `Page.getFrameTree` з попередньої діагностики (CFT 151 та ізольований Chrome 154) пояснено очікуванням macOS Keychain для профілю з підміненим HOME. Сирі докази тих спроб — у `.scratch/chrome-control-page-fix-20261009/` та `.scratch/chrome-profile-network-ZZqQ7U/proof.json`.

Попередній R2 packaged server/web UI proof лишається доказом лише незмінених UI owner/layout станів: 16/16 по 368, 375, 1024 і 1440 px, два seeded artifacts, API bytes та mode-command no-second-dispatch (`.scratch/chrome-ui-proof-aROuMq/proof.json`). Це не свіжий R4 browser-runtime або native Tauri proof. Особистий Chrome не підключали: користувацька remote-debug configuration і Chrome permission prompt не підтверджені. Також не доведено зовнішню live vision для image-capable provider або native Tauri runtime.
