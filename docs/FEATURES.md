## Providers: деталі

**Local CLIProxyAPI.** [CLIProxyAPI 8.0.13](https://github.com/router-for-me/CLIProxyAPI/releases/tag/v8.0.13) на `http://127.0.0.1:8319/v1`. Private binary, `config.json`, `connection.json` і OAuth `auth/` — у `DATA_DIR/cliproxyapi` (для `npm start` це `.data/cliproxyapi`); binary звірено з official release SHA-256, credentials не входять у Git чи package.

- Startup перевіряє deployment, запускає власну process group, чекає authenticated readiness і підключає каталог без model prompt. Якщо проксі вже працює з власним ключем, Sigma бере його без нового процесу й не завершує. Власний процес завершується після drain чатів; watchdog прибирає його після аварії server/native parent. Зайнятий порт не звільняється примусово.
- Відсутнє/неповне розгортання не блокує інші провайдери; startup не завантажує binary і не переносить OAuth між data directories.
- Helper: `node scripts/cliproxy-local.mjs start` (terminal лишити відкритим) і `login` (Google consent; callback тимчасово на порту 51122). Startup і helper мають спільні перевірки: private файли, pinned binary, loopback host, вимкнені management/plugins/G1 credit fallback, обмежений environment, raw logs вимкнені.
- UI: **Providers → Local model gateways → Antigravity · local CLIProxyAPI**: connected після startup; **Connect local proxy**, **Refresh models**, **Disconnect** (чекає drain), **Cancel request** (catalog action; chat **Stop** — відповідь).
- Provisioning/lifecycle: startup завжди створює private `cliproxyapi/{bin,auth}` (0700), `config.json`+`connection.json` (0600, випадковий local key; існуючі не перезаписуються; `auth/` лише рахується) і копіює pinned binary з `SIGMA_CLIPROXY_BINARY`/bundled `resources/cliproxyapi` при збігу SHA-256, але процес proxy запускається лише за opt-in: `cliproxyapi/enabled.json` (0600, типово off) ставить `POST /api/cliproxy/connect`, скидає `disconnect` (зупиняє власний процес; чужий/borrowed не чіпає; connect після disconnect знову стартує в тому ж запуску). Без opt-in стан `stopped` («Local proxy is off…»); існуючі інсталяції з `auth/` без прапора мігруються в on. Стан у `/api/cliproxy` → `provider.proxy`: `not_installed|needs_login|starting|ready|degraded|stopped|borrowed` + reason (Providers показує). Власний процес: ≤3 рестарти/5 хв з backoff, потім `degraded`; health `/models` кожні 30с; чужий listener (8317 чи будь-який) не зупиняється й не рестартується. Desktop build додає binary в DMG з `SIGMA_CLIPROXY_BINARY` або за замовчуванням з `.data/cliproxyapi/bin` (hash і licences перевіряються).
- Transport — OpenAI-compatible Pi SDK; tools пропонує модель, виконує Pi після approvals. Каталог містить лише IDs: context 32,768, output 4,096, без reasoning controls; cost невідомий (нульові counters не означають безкоштовний upstream).
- Для native Tauri `DATA_DIR` — app-data; source `.data` не доводить native provisioning. Helper приймає `SIGMA_DATA_DIR`.

**Claude Code CLI.** Після restart знову **Refresh status** (збережений enabled route перевіряє account лише за цією дією; Connect потрібен тільки для disabled route). Login required → завершити вхід в офіційному CLI і refresh. CLI шукається також у `~/.local/bin`. **Cancel operation** скасовує status/Connect probe; chat **Stop** завершує власний CLI request і helpers.

**Direct AGY (blocked).** **Prepare / recheck private profile** готує Sigma-owned приватний HOME; видану команду запускати в локальному terminal. Settings після native sign-in можуть містити лише trusted HOME без default false `useG1Credits` — Sigma приймає цей sparse формат. `agy 1.2.16`: `init.tools` — global inventory, effective restrictions не доведено; sign-in route не вмикає. Demo/`PI_OFFLINE=1` native CLI не запускає.

**Antigravity (unsupervised).** Окремий opt-in (Providers → Antigravity (unsupervised), вимкнено за замовчуванням; потрібні checkbox і підтвердження, стан у `native-providers.json`). AGY сам виконує свої file/shell/browser tools **без Pi Allow/Deny**; Sigma бачить лише те, що AGY повідомляє (`step_update.tool_info`), і показує це read-only як «Executed by AGY (unsupervised)» в Activity та badge у chat header/Graph. AGY запускається з дефолтним main agent (без `--agent`: кастомні агенти обмежують tools, перевірено live на agy 1.2.17); старий `sigma-antigravity-unsupervised.md` у профілі Sigma видаляється. Вимкнено → моделей немає (unregister); увімкнення/вимкнення Stop-ає активні AGY runs.
- Лише нові **code**-сесії в ізольованому **worktree**; direct/read-only, parallel/children, delegation і reviewer/QA children — відмова. Workspace не може дорівнювати чи містити DATA_DIR, agent dir, credential roots чи `$HOME`. Policy snapshot має `unsupervised:true`. Worktree ділить Git object store/refs із source, тож AGY технічно може змінити branches source repo.
- Transport: `agy -p --input-format stream-json --output-format stream-json --sandbox --dangerously-skip-permissions --agent sigma-antigravity`, cwd = workspace, HOME = приватний профіль, env allowlist (`HOME PATH TMPDIR USER LANG LC_ALL AGY_CLI_DISABLE_AUTO_UPDATE`), власна process group через native-cli watchdog (Stop/Quit/SIGKILL drain). Профіль лишається fail-closed (`tools: []`, deny-правила) — це може обмежувати AGY. Settings після sign-in у sparse-формі (без `hooks`/`useG1Credits`, інший порядок deny) приймаються, будь-яке послаблення відхиляється.

**Pi SDK sign-in.** **Cancel sign-in** скасовує взаємодію до повернення credentials; якщо SDK save/model sync уже почався — чекає його завершення. Configured — стан конфігурації, не гарантія доступної моделі чи строку дії. Застарілі status/model відповіді не замінюють новий login/вибір моделі; помилки показуються без приватного auth content.

**Agents.** Проста відповідність роль → модель + reasoning для planner, researcher, worker (Implementation), reviewer, QA; без instructions. Явна модель має підтримувати рівень; для "Same as chat model" непідтримуваний рівень замінюється на default моделі. Модель чату є оркестратором (root і coordinator завжди на ній) і сама обирає, яких агентів викликати за розміром задачі. Недоступна configured model дає явну помилку. Старі каталоги з групами нормалізуються при читанні.

## Git у сесії

Права панель → **Repository**: гілка, HEAD, кількість змін, ahead/behind; перемикання локальної гілки, **Pull** (лише fast-forward), **Push** (без upstream — у `origin` з налаштуванням upstream), **Commit** (сесії, що редагують вибрану папку напряму, зокрема Parallel code). Commit: кнопка просить агента написати message і викликати `git_commit`; виконується лише після погодження. Switch/Pull/Commit можливі, коли жодна сесія чи делегований агент цієї папки не працює й не чекає approval; у Parallel code вони ще чекають, поки зміни worker-а з окремого worktree буде злито або відхилено (його merge потребує спільного base commit; конфлікт не блокує), Push — ні; після зміни HEAD direct-сесії переходять на новий HEAD. Git-хуки не запускаються. У порожньому чаті (без сесії) вкладка Repository працює з вибраною папкою: статус, перемикання гілки, Pull і Push з тими самими перевірками; Commit — лише в чаті, бо message пише агент. **Stashes**: список stash (повідомлення, гілка, час), **Stash changes** (разом з untracked, ignored лишаються) з необов'язковим повідомленням, **Apply** (stash лишається), **Pop**, **Drop** (з підтвердженням); stash іде тим самим durable журналом і перевірками, що Pull, але не чекає на злиття worker-ів, бо HEAD не рухає; Apply/Pop/Drop вказують stash за ref і commit, тож змінений список відхиляється. **Worktrees**: список лише для перегляду — шлях, гілка або detached, HEAD, позначки «this folder», «Sigma workspace», locked, prunable. Для worktree-сесій дії вимкнені — спершу Source Apply. Потрібен canonical repository root; у Read-сесії на вкладеній папці controls вимкнені з причиною. Symlink-аліаси canonicalize-яться.

**Exact approval.** Показуються повний message, native Git diff, parent і immutable tree. Погоджені UTF-8 bytes фіксуються в приватному `DATA_DIR/git-intents`; HEAD і реальний index не змінюються до дозволу. Зміна HEAD, branch, index, набору файлів, bytes, mode чи path identity відхиляє preview. Unsupported/omitted файли й D/F-конфлікти зі сторонніми staged шляхами відхиляються; сторонні index entries і flags зберігаються. Hooks, external diff, textconv, clean filters не виконуються; user identity і commit signing збережено.

**Durable commands і unknown.** Commit/Pull/Switch мають command ID: повтор не виконує Git знову, інший request з тим самим ID відхиляється. Після crash чи непевного результату **Repository → Unknown Git** показує intent і свіжі HEAD/tree observations; **Inspect fresh Git state** → **Acknowledge observed state** завершують reconciliation без повтору. Unknown блокує нові HEAD moves і прямі записи в цьому root (навіть якщо належить Read-сесії). Непідтверджена process identity, живі descendants, foreign/replaced lock/index чи divergent HEAD лишають recovery inspect-only; довільні Git locks не видаляються. Stop/Quit дочікуються finalizer; hung Git process group має bounded timeout. Push — окрема явна дія, не входить до durable HEAD-moving gate.

## Проєкти та multi-repo

**Projects → New project → Choose folders…** (системний NSOpenPanel, можна кілька; **Add folders**/**Remove**); 1–20 каталогів, у т.ч. без Git; дублікати й symlink-аліаси зводяться до canonical шляху. Панель репозиторію: гілка/detached, staged/unstaged/untracked, конфлікти, ahead/behind відносно upstream (**Refresh Git** без fetch/pull/push). Project фільтрує сесії; **Use for chat** підставляє папку в **New session**. Перемикання групи ховає несумісний чат, не зупиняючи run; чернетка живе до reload. Cookie прив'язані до порту.

**New multi-repository task**: Project із 2–4 окремих Git-репозиторіїв, кожен з хоча б одним commit. Задача фіксує roots і HEAD; пізніша зміна Project її не змінює. Координатор без файлового доступу делегує за ID репозиторіїв: на кожен — Parallel Code сесія у вибраній папці (worktree — явний вибір). Картки показують результат, diff, check/review; **Open repository** відкриває approvals/merges. Stop координатора зупиняє активні сесії репозиторіїв. Атомарної операції між репозиторіями немає; перервана задача стає `unknown` без повторного створення worktree.

## Зміни коду

**Code**: корінь Git-репозиторію з хоча б одним комітом. Типово — прямо у вибраній папці (dirty/untracked на місці, кожен запис потребує дозволу). **Workspace → Git worktree** — окремо від поточного HEAD у `DATA_DIR/workspaces/<session-id>` без dirty/untracked. Старі сесії в незалежних копіях працюють за старою схемою.

Потік: описати зміну → **Allow once** на читання → перевірити diff → **Apply this change**; **Deny**/**Stop** скасовують запис. **Run details → Code changes** показує diff від початкового HEAD і **Download patch** (у direct режимі може містити правки, що існували до сесії).

**Parallel code**: root у вибраній папці. Єдиний writer (worker) редагує робочу копію root напряму, без worktree і merge. Якщо worker делегується, поки інший worker того ж root ще працює, він отримує окремий worktree з одного commit; після завершення за повного доступу (Full access) його зміни автоматично зливаються в робочу копію root тим самим механізмом (журнал позначає merge як `auto`), а за Ask mode або при конфлікті/помилці merge лишається для користувача, і результат delegate прямо про це каже. Далі вручну: **Prepare merge** → three-way preview (конфлікт `root/base/worker` не пишеться) → **Apply to root** лише погодженого preview. Старі checks/review після merge stale. Merge не чіпає index/commit/push; видалення, mode changes, binary/великі файли не підтримуються. При crash картка стає `unknown`/`partial` з фактичними хешами; **Acknowledge observed root state** розблоковує нове зведення без повтору записів. Worktree і preimage лишаються на диску, автоматичного cleanup немає.

**Controlled Node check**: відносний `.test.mjs` + файли-імпорти → **Prepare check** (точні `argv`, snapshot cwd, ревізія, файли/hash, ліміт 30 с і 64 KiB) → **Approve and run** (`node --test --test-isolation=none --test-reporter=tap` в окремому snapshot); **Deny/Stop check**. **TypeScript check**: `tsconfig.json` з явним `files`, без `include`/`extends`/`references`; локальний `typescript` копіюється в snapshot, `tsc --noEmit`. npm scripts і весь репозиторій не запускаються. Після check — **Start independent review**: окрема Pi сесія лише з `read`/`ls`; текст reviewer — порада, не PASS. Після виправлення потрібні новий check і review (старі stale).

**Source Apply** (worktree або стара копія; потрібні passed check + завершене review): картка з оригінальним шляхом, branch/HEAD, ревізією, файлами, mode, SHA-256 і diff; окремий дозвіл переносить 1–20 текстових add/update файлів. Перед кожним записом звіряються HEAD/branch, index, вміст і mode цілі та ізольованої папки; сторонні staged/unstaged/untracked і index не змінюються. Конфлікт чи unknown зупиняє перенесення зі збереженням preimage і receipt, без автоповтору; **Acknowledge these source observations** не пише файлів. У direct режимі Source Apply немає. Одночасний інший writer між перевіркою та rename — гонка host filesystem: закрити інші writers.

**Інструмент `bash` («Run command»).** Агенти (root Code/Parallel, planner, researcher, worker, reviewer, QA; не AGY unsupervised, не multi-repo coordinator) виконують shell-команди на хості: `/bin/zsh -lc` у папці агента, з мережею та оточенням без `SIGMA_*`/`PI_*`/ключів провайдерів. Запуск під macOS `sandbox-exec`: заборонено читання/запис лише credential-файлів (`auth.json`-типу, `~/.codex/auth.json`, `~/.gemini/oauth_creds.json`, `~/.cli-proxy-api/`, `agent-access.json`, `native-providers.json`, `state.sqlite`, sign-in-папки CLIProxyAPI/Antigravity, key-файли Pi SDK); решта папок доступна; без `sandbox-exec` — відмова. Ask-режим: Allow/Deny з повною командою; Full access: без запиту, але в Approvals/Activity (команда й код виходу). Тайм-аут 300 с (до 1800 с), вивід — останні 30 KB, група процесів завершується за тайм-аутом, Stop і при виході. **Увага:** команда може змінити все, що доступно вашому користувачу поза credential-файлами.

**Ліміти.** Writer: `read`/`ls`/`edit`/`write`/`bash`, UTF-8 до 128 KiB, diff до 256 KiB на дозвіл. Node check до 20 файлів; TypeScript — до 199 input files. macOS `sandbox-exec`: без home credentials/мережі, запис лише в snapshot; на непідтриманій системі check завершується без unsandboxed fallback. Snapshot без `.git`. Pending check після restart — expired, незавершений — unknown; watchdog завершує тест при втраті server. Reviewer: 300 с, 1 одночасно, 4 на Code сесію. Patch: до 200 files / 1 MiB; omitted files (напр. mode changes) блокують patch і checks. Worktree не ініціалізує submodules/LFS. Загальний shell і npm scripts недоступні.

**Write guards.** Перевіряються шлях і hash після дозволу; блокуються symlinks/hardlinks, Git metadata, sensitive paths, `.pi-edit-*`; у direct режимі також Git-ignored файли (використати worktree). `applied` — durable receipt, `failed` — не завершено; невизначений direct write після crash показує stored/current hash/mode і потребує явного підтвердження без повтору. Temp-файли від crash і незображувані mode changes пропускаються (patch/checks недоступні). Це host-перевірки, не OS sandbox проти іншого локального процесу.

## Browser QA (S1)
- Вкладка Changes → «Browser QA»: користувач запускає run для статичного сайту (entry, напр. `index.html`); сам POST `/api/sessions/:id/qa/runs` (X-Command-Id) є схваленням run: заморожується поточна Code-ревізія, файли workspace (без `.git`, `node_modules`, секретів, symlink) копіюються у read-only preview з manifest-hash, а Chrome for Testing (`SIGMA_QA_CHROMIUM`, sha256 виконуваного файлу записується) стартує в ізоляції «outer»: `sandbox-exec` SBPL + `--no-sandbox`, мережа лише до preview-порту.
- Агентські інструменти `qa_navigate`, `qa_click`, `qa_type`, `qa_screenshot`, `qa_assert` існують лише в child-сесіях ролі `qa` за наявності схваленого активного run; navigate/click/type потребують окремого approval (прив'язаного до run, ревізії, manifest-hash, target, observation). click/type вимагають observation (з `qa_screenshot`) новішого за останню навігацію/дію, інакше відмова без CDP-виклику. Дія записується як `dispatched` ДО CDP-відправки; після краху/рестарту — `unknown`, run блокується, replay заборонений.
- Скріншоти: `<DATA_DIR>/qa/<runId>/artifacts/<sha256>.png` + метадані (mime, width, height, sha256, bytes, revision, manifestHash, viewport, observationId); у tool-результатах і SSE лише id/метадані. `GET /api/sessions/:id/qa/artifacts/:id` — `image/png`, `nosniff`, та сама автентифікація.
- Stop/Quit/Cancel закривають групу процесів браузера до закриття Storage.

## QA gate (S2)
- `qa_finding` (qa-агент, read-only щодо браузера): {summary, severity, artifactIds, actionIds} — лише завершені assert-дії та скріншоти активного run; ідемпотентно за tool call; finding `current` лише поки його ревізія = поточна Code-ревізія. `GET /api/sessions/:id/evidence` повертає `qaRuns`/`qaFindings` з тим самим правилом current/stale; Changes показує stale-маркер.
- `qa_view_artifact{artifactId}` — лише для незалежного revision-reviewer: артефакт мусить належати цій сесії та run тієї ж ревізії/manifest; hash і PNG-заголовок перевіряються при кожному читанні; image-блок лише якщо модель приймає зображення, інакше метадані. Перегляд — durable-факт (`qa_views`).
- Gate `GET /api/sessions/:id/qa/gate` (read-only; UI «QA gate»): `r1_failed → finding_recorded → caller_receipt → fix_approved → r1_stale → r2_passed → reviewed → final_receipt`. Кроки виводяться з durable-фактів (qa_runs/actions/artifacts/findings, graph_fact з `receiptEntryId` з native `turn_end`, схвалені записи/merge, reviews + qa_views, entry ID перевіряється у JSONL сесії); записуються лише нові віхи (монотонно, у `qa_gates`). `unknown` на будь-якому кроці блокує з явним станом; нічого не replay-иться. Prose/`settled`/dispatch не просувають `caller_receipt`/`final_receipt`.

## Делегування й Stop

- Нові Read-only та Parallel Code сесії — policy v2: глибина 2 (root=0, child=1, grandchild=2), без ліміту кількості агентів (descendants, revision reviewers і одночасних child/reviewer runs), timeout 300 с на child. Старі v1/null snapshots не розширюються. Кожен child має власну Pi session; модель — зі збереженої відповідності роль → модель, reasoning — з ролі, execution — host. Nested writer (worker, делегований іншим worker-ом) редагує робочу копію батька напряму, якщо жоден інший worker того ж root не працює; інакше отримує окремий worktree, який автоматично не зливається.
- **Run details → Agent tree → View result and message**: історія child; у running child — **Steer current turn** / **Follow up after current turn**; після `settled` — нове уточнення тій самій дитині . Повідомлення мають durable command ID: `queued` ≠ доставка, `unknown` не повторюється. Revision-bound Code reviewer повідомлень не приймає.
- **Session policy**: immutable snapshot requested/effective model/workspace/profile; для старих сесій — unknown, без вигаданої історії.
- **Stop child** зупиняє вибрану дитину і нащадків (включно з очікуванням approval і створенням runtime); reviewer — **Stop review**. Загальний Stop скасовує активних нащадків і за settled/idle root, зберігаючи завершені результати. Невизначений результат Stop не повторюється.
- `settled` — завершення Pi run, не успіх engineering задачі; результат child — не незалежне review.
- Команди мають client idempotency ID; Pi preflight rejection лишає prompt у редакторі. Після crash `dispatched`/`queued` → `unknown` без replay. `delegate`/`edit`/`write` пишуть `toolCallId` до виконання; той самий виклик не повторюється. **Run details → Unresolved activity**: до 100 unknown inputs і tool calls. Pending approvals після restart — `expired`.

## Відновлення й архівування

Невизначені inputs/tool calls оглядати в **Unresolved activity**; для запису — **Review observed state → Acknowledge observed state · no replay**. **Workspace setup recovery → Inspect workspace identity** → **Continue setup** (ті самі session/manager IDs, без replay prompt; multi-repo — **Continue verified setup · no prompt replay**); ambiguous legacy setup — inspect-only. **Archive/Restore** (також для tasks) оборотні й змінюють лише DB; active/unknown робота в дереві блокує archive; це не cleanup worktree.

## Guarded cleanup архівних сесій

Sidebar → Archived → "Clean up archived sessions…". `GET /api/cleanup/preview` (read-only) повертає candidates (чисті зареєстровані worktree у `workspaces/<id>` та scratch `checks/<id>`, `reviews/<id>` архівних owners), blockers і `digest`. `POST /api/cleanup` (`X-Command-Id`, `{digest, approve:true}`) перераховує preview, відмовляє при іншому digest, працює під admission, викликає `git worktree remove` без `--force`; гілки, DB-рядки, Pi history, source-applies/worker-merges/git-intents не чіпає. Dirty/untracked/index, HEAD ≠ base, неархівований owner, активна робота, unknown/partial рядки та невідомі директорії — blockers. SIGKILL посеред видалення → durable `cleanup` command стає unknown, не повторюється, його шляхи лишаються blockers. Worktree allocation (`worktree add`/`checkout`) іде в тій самій detached supervised групі: Stop її скасовує, смерть сервера її завершує, частковий worktree ніколи не видаляється автоматично.

## Legacy import (CLI)

Один зупинений legacy `DATA_DIR` (`.data` або `work/tauri-data`) → порожній native DATA_DIR. Копіюються лише `state.sqlite` і `sessions/*.jsonl`; credentials, workspaces, Git — ні (імена лише у звіті). Старий Sigma треба зупинити самому: held source/destination відхиляється, процеси не вбиваються.

1. `npm run migrate:preview -- --source <dir> [--dest <dir>] [--stage-root <dir>]` — read-only capture у stage (`<dest>-migration/<stageId>`, або `SIGMA_MIGRATION_STAGE`), `preview.md/json`, SHA-256 звіту, blockers/warnings. Dest за замовчуванням `SIGMA_DATA_DIR` або `~/Library/Application Support/dev.sigma.app`; джерела не зливаються.
2. `npm run migrate:stage -- --source <dir> --authorize <sha256> [--accept-alias <ids>] [--accept-missing-history <ids>]` — повторний capture; хеш має збігатися, всі blockers мають бути прийняті явно (alias — стара `pi-orchestrator` директорія; missing — рядок імпортується без змін). Destination не змінюється.
3. Публікація лише при старті: `SIGMA_MIGRATE_PUBLISH=<stageId> SIGMA_DATA_DIR=<dest> [SIGMA_MIGRATION_STAGE=<root>]` під lease, до Storage; dest має бути порожнім. Журнал `.migration-journal.json` — незавершений блокує старт без replay/rollback; `state.sqlite.pre-migration` зберігається.
4. `npm run migrate:status` — stages, журнал dest.

Переписуються тільки `sessions.file` та `managerDir` у policy/command setup/task data; IDs і JSONL байти незмінні. Drift, ненульовий source WAL, ambiguity або integrity помилка блокують stage.
